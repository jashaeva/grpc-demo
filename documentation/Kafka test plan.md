# Тест план тестирования работы Kafka

Имеется **минимальная конфигурация** Кафки:
- **1 топик**, **1 партиция** (важно: партиция одна, иначе консьюмер не увидит данные).
- **1 продьюсер** (без реплик, `replication.factor=1`).
- **1 консьюмер**.
- **gRPC-сервис** → пишет в Кафку.
- **REST-модуль** → читает из Кафки и отдает данные наружу.

### ✅ Жирным выделено — проверять **строго обязательно**
### 🔘 Обычным шрифтом — можно проверить, но риск невелик (пропустить)

## 1. Kafka Producer (gRPC → Кафка)

| #          | Проверка | Обязательно? | Пояснение |
|:-----------| :--- | :--- | :--- |
| **T-KP1**  | **Отправка валидного сообщения из gRPC → топик** | ✅ **ДА** | Базовый сценарий. Без этого весь смысл теряется. |
| **T-KP2**  | **Отправка с пустым (null) значением** | ✅ **ДА** | gRPC может прислать пустой запрос — приложение не должно падать. |
| **T-KP3**  | **Отправка очень большого сообщения (например, 10 МБ)** | 🔘 По желанию | Если бизнес-логика не предполагает больших сообщений — можно пропустить. Но если gRPC принимает файлы — проверьте. |
| **T-KP4**  | **Некорректный JSON в теле запроса** | ✅ **ДА** | gRPC-сервис должен **не упасть**, а вернуть ошибку клиенту. Продьюсер должен залогировать ошибку сериализации. |
| **T-KP5**  | **UTF-8 с эмодзи/спецсимволами** | 🔘 По желанию | Если в gRPC передаются тексты — проверьте. Если только числа/ID — пропустите. |
| **T-KP6**  | **Acks=1 (умолчание). Отправка при живом брокере** | ✅ **ДА** | Проверьте, что лидер подтверждает запись. |
| **T-KP7**  | **Retries. Имитация временной недоступности брокера (сетевой обрыв на 1-2 сек)** | ✅ **ДА** | Продьюсер должен переотправить сообщение (ретраи) и не уронить gRPC-сервис. Клиент должен дождаться ответа или получить таймаут. |
| **T-KP8**  | **Превышение `max.block.ms` (брокер надолго упал)** | ✅ **ДА** | gRPC-сервис не должен висеть бесконечно. Должен вернуть ошибку клиенту через разумное время (например, 5-10 секунд). |
| **T-KP9**  | **Callback при успешной отправке (метаданные)** | 🔘 По желанию | Если у вас асинхронная отправка — проверьте, что callback вызывается. Если синхронная — можно пропустить. |
| **T-KP10** | **Callback при ошибке** | ✅ **ДА** | gRPC-сервис должен получить исключение и вернуть клиенту ошибку, а не "проглотить" её. |

## 2. Kafka Consumer (Кафка → REST)

| #                   | Проверка | Обязательно? | Пояснение |
|:--------------------| :--- | :--- | :--- |
| **T-KC1**           | **Чтение валидного сообщения из топика и отдача через REST** | ✅ **ДА** | Базовый сценарий. REST должен вернуть данные. |
| **T-KC2**           | **Чтение битого/невалидного сообщения** | ✅ **ДА** | **Критично!** Если в топик попало плохое сообщение, консьюмер **не должен падать** бесконечно. Он должен залогировать ошибку и либо пропустить, либо уйти в DLQ. Иначе REST-модуль ляжет намертво. |
| **T-KC3**           | **Чтение null-значения** | ✅ **ДА** | REST не должен падать с NPE при обработке null. |
| **T-KC4**           | **Auto-commit (включен по умолчанию)** | ✅ **ДА** | Проверьте, что оффсеты коммитятся автоматически. После перезапуска консьюмер не читает старые сообщения. |
| **T-KC5**           | **Ручной коммит (sync) — если вы его используете** | 🔘 Если есть | Если в коде есть `commitSync()` — проверьте, что он вызывается после успешной обработки. Если auto-commit — пропустите. |
| **T-KC6**           | **Падение обработки до коммита** | ✅ **ДА** | Если REST-модуль упал во время обработки сообщения, после перезапуска **это же сообщение должно прочитаться снова** (at-least-once). Это гарантирует, что вы не потеряете данные. |
| **T-KC7**           | **Внезапное отключение консьюмера (kill -9)** | ✅ **ДА** | После перезапуска REST-модуль должен **продолжить чтение с последнего закоммиченного оффсета**, а не с начала. Иначе получите дубли. |
| **T-KC8**           | **Долгая обработка сообщения (> `max.poll.interval.ms`)** | ✅ **ДА** | Если REST обрабатывает запрос долго (например, 5 минут), консьюмер должен **не упасть** с `LeaveGroupException`. Нужно либо увеличить таймаут, либо использовать паузу. |
| **T-KC9**               | **Consumer.pause() при перегрузке REST** | 🔘 По желанию | Если REST-модуль отдает данные наружу и БД/внешний API тормозит — полезно проверить. Но для MVP можно пропустить. |

## 3. Сквозные проверки (gRPC → Кафка → REST)

| #          | Проверка | Обязательно? | Пояснение |
|:-----------| :--- | :--- | :--- |
| **T-KPC1** | **Порядок сообщений** | ✅ **ДА** | Поскольку у вас 1 партиция, порядок **гарантирован**. Проверьте, что REST читает в том же порядке, в котором gRPC отправил. |
| **T-KPC2**    | **Дубли при перезапуске консьюмера** | ✅ **ДА** | Отправьте сообщение → выключите REST-модуль ДО коммита → включите снова. REST должен **прочитать это же сообщение повторно**. Если он его пропустил — вы потеряли данные. Если прочитал дважды — это нормально (at-least-once), но бизнес-логика должна быть идемпотентной. |
| **T-KPC3**    | **Нагрузка (например, 10 000 сообщений)** | 🔘 По желанию | Для продакшена — обязательно. Для тестового стенда — можно пропустить, но желательно проверить, что консьюмер не отстаёт (Lag = 0). |

## 5. Логирование и наблюдаемость (для отладки)

| #         | Проверка | Обязательно? | Пояснение |
|:----------| :--- | :--- | :--- |
| **T-KL1** | **Логирование при ошибке сериализации** | ✅ **ДА** | Чтобы понять, какое именно сообщение сломало консьюмера. Должны быть видны: топик, партиция, оффсет. |
| **T-KL2** | **Логирование при успешном коммите оффсета** | 🔘 По желанию | Полезно для отладки дублей, но не критично. |
| **T-KL3** | **Метрики (Lag, скорость потребления)** | ✅ **ДА** | Хотя бы базовые — чтобы видеть, что REST-модуль не отстаёт. |

## ИТОГОВЫЙ МИНИМАЛЬНЫЙ ЧЕК-ЛИСТ (ТО, ЧТО НЕЛЬЗЯ ПРОПУСТИТЬ)
 
### Для gRPC-продьюсера:
1. TC-KP01 Отправка валидного сообщения.
2. TC-KP02, T-KP04 Отправка пустого тела.
3. TC-KP04 Отправка невалидного JSON — gRPC не должен упасть.
4. TC-KP07 Временная недоступность брокера — ретраи работают, gRPC не висит вечно.
5. TC-KP08 Долгая недоступность брокера — таймаут, gRPC возвращает ошибку.

### Для REST-консьюмера:
6. TC-KC01 Чтение валидного сообщения и отдача через REST.
7. TC-KC02 Чтение битого сообщения — консьюмер **не падает в цикле** (логирует и пропускает).
8. TC-KC04 Auto-commit работает — после перезапуска старые сообщения не читаются.
9. TC-KC06 Если обработка упала до коммита — после перезапуска сообщение читается снова (не потеряно).
10. TC-KC08 Долгая обработка — консьюмер не уходит из группы (`max.poll.interval.ms` не превышен).

### Сквозные:
11. TC-KPC01 Порядок сообщений соблюдается (1 партиция → гарантирован).
12. TC-KPC02 Дубли при перезапуске — проверка стратегии at-least-once.
