
# Инструкция по Kafka 

Собственно Kafka запускается как докер-образ вместе с zookeeper и работает на порту localhost:9092. Настройки в файле (лежит в корне).

В проекте: 
1. подключить зависимость  `org.springframework.kafka:spring-kafka`,
2. настроить в файлах application.yaml  в свойстве **kafka**  свойства topic, producer, consumer. 
3. Описать процесс отправки сообщения для @KafkaTemplate (producer)
4. Описать процесс "слушания" сообщения для @KafkaListener (consumer)

При старте приложения спринг бут самостоятельно создаст бины, которые нужны для дальнейшей работы. 


Задача в проекте:

Логирование через Kafka
При выполнении любого gRPC-вызова на grpc-server сервер отправляет событие 
(например, "Вызов метода X с параметром Y") в топик Kafka. rest-client может подписаться на этот топик и
выводить в консоль все вызовы, которые дергает gRPC-сервер.

# Тестирование Kafka (полный список)
Ниже приведен **базовый (обязательный) чек-лист** нефункциональных и инфраструктурных проверок для Kafka-компонентов.
Эти тесты должны проходить **до** написания бизнес-логики.

---

### 1. Тестовые случаи для Kafka Producer (Продьюсер)

Цель: проверить, что продьюсер корректно отправляет данные, переживает сбои и не теряет сообщения на этапе отправки.

#### А. Базовая отправка (Happy Path)
| # | Проверка | Ожидаемый результат |
| :--- | :--- | :--- |
| 1.1 | Отправка сообщения с валидным ключом и значением. | Сообщение появляется в указанном топике (утилитой `kafka-console-consumer`). |
| 1.2 | Отправка пустого (null) значения. | Сообщение отправляется (в Kafka это допустимо, если поле value null). |
| 1.3 | Отправка очень большого сообщения (например, 5 МБ, если лимит топика 10 МБ). | Отправка успешна (если не превышен `max.request.size`). |

#### Б. Сериализация (Serialization)
| # | Проверка | Ожидаемый результат |
| :--- | :--- | :--- |
| 1.4 | Отправка объекта с некорректным JSON (например, невалидная дата). | Продьюсер **не падает**, а логирует ошибку сериализации (Serializer Exception). |
| 1.5 | Отправка строки с нестандартной кодировкой (UTF-8 с эмодзи/иероглифами). | Данные передаются без искажений (проверить Hex-дамп). |

#### В. Конфигурация и Параметры (Acks & Retries)
| # | Проверка                                                                                    | Ожидаемый результат |
| :--- |:--------------------------------------------------------------------------------------------| :--- |
| 1.6 | **Acks=all / -1** (минимальная репликация). Отправка при 1 живом брокере (из 3).            | Сообщение отправлено, т.к. ISR содержит минимум 1. |
| 1.7 | **Acks=all**. Отправка при падении всех брокеров, кроме лидера (ISR < min.insync.replicas). | Продьюсер получает исключение `NotEnoughReplicasException`. |
| 1.8 | **Retries > 0**. Имитация временного сетевого обрыва (брокер недоступен 1 сек).             | Продьюсер переотправляет сообщение (ретраи), и оно уходит после восстановления. |
| 1.9 | **Idempotence=true**. Отправка дубля сообщения после ретрая.                                | Дубль не появляется в топике (Sequence Number сбрасывается). |

#### Г. Таймауты и Блокировки
| # | Проверка | Ожидаемый результат |
| :--- | :--- | :--- |
| 1.10 | Превышение `max.block.ms` (буфер продьюсера переполнен, а брокер недоступен). | Выбрасывается исключение `TimeoutException`, отправка прерывается. |
| 1.11 | Отправка c Callback-ом. Проверка `RecordMetadata` (offset, partition). | Callback вызывается, метаданные не равны null (для успешной отправки). |
| 1.12 | Отправка с Callback-ом при ошибке (Exception в `onError`). | Callback вызывается с исключением (не должен висеть бесконечно). |

### 2. Тестовые случаи для Kafka Consumer (Консьюмер)

Цель: проверить, что консьюмер читает данные, управляет смещениями (offsets), корректно перезапускается и не вносит дубли в целевую систему.

#### А. Чтение и Десериализация
| # | Проверка | Ожидаемый результат                                                               |
| :--- | :--- |:----------------------------------------------------------------------------------|
| 2.1 | Чтение валидного сообщения из топика. | Сообщение сконвертировано в целевой объект (POJO) без ошибок.                     |
| 2.2 | Чтение "мусорного" сообщения (невалидный формат) в топике. | Консьюмер **не падает**, ошибка логируется, обработка прерывается или идет в DLQ. |
| 2.3 | Чтение сообщения с null-ключем. | Обработка выполняется (null допустим).                                            |
| 2.4 | Чтение сообщения с пустым значением (tombstone). | Обработчик получает null и корректно это обрабатывает (не падает с NPE).          |

#### Б. Управление Offset (Commit) — Критично!
| # | Проверка | Ожидаемый результат |
| :--- | :--- | :--- |
| 2.5 | **Auto-commit = true** (умолчание). Чтение пачки сообщений. | Offset автоматически фиксируется через `auto.commit.interval.ms`. |
| 2.6 | **Manual commit (sync)**. Чтение сообщения, успешная обработка. | Offset закоммичен. При перезапуске консьюмер не читает это сообщение заново. |
| 2.7 | **Manual commit (async)**. Обработка упала с ошибкой. Коммит не вызван. | При перезапуске консьюмер читает **то же самое** сообщение (at-least-once). |
| 2.8 | **Batch processing**. Чтение 100 сообщений, обработка 50-го упала. | Вариант А: коммитим все (потеря данных). Вариант Б: не коммитим ничего (дубли). Проверяем выбранную стратегию. |

#### В. Перебалансировка (Rebalance) и Параллелизм
| # | Проверка | Ожидаемый результат |
| :--- | :--- | :--- |
| 2.9 | Запуск 2-х инстансов консьюмера в одной группе (топик с 2 партициями). | Каждый читает свою партицию, обработка идет параллельно. |
| 2.10 | Добавление 3-го консьюмера в группу (партиций всего 2). | Один консьюмер остается в состоянии Idle (не читает). |
| 2.11 | Внезапное отключение одного консьюмера (kill -9). | Через `max.poll.interval.ms` происходит перебалансировка, партиция уходит живому консьюмеру. Обработка не останавливается навсегда. |
| 2.12 | Долгая обработка сообщения (> `max.poll.interval.ms`, например, 5 минут). | Консьюмер считается мертвым, происходит ребаланс, партиция уходит другому потребителю (избегаем "зомби"). |

#### Г. Пауза (Pause/Resume) и Backpressure
| # | Проверка | Ожидаемый результат |
| :--- | :--- | :--- |
| 2.13 | Если целевая БД перегружена, вызывается `consumer.pause()`. | Потребление из партиций останавливается (poll возвращает 0 записей). |
| 2.14 | После восстановления БД вызывается `consumer.resume()`. | Потребление возобновляется с того же смещения. |

### 3. Сквозные (End-to-End) проверки для обоих компонентов

| # | Проверка | Ожидаемый результат |
| :--- | :--- | :--- |
| 3.1 | **Ordering**. Отправка 3 сообщений с одинаковым ключом (`key=1`) в 1 партицию. | Консьюмер читает их **строго в порядке отправки** (Sequence numbers не нарушены). |
| 3.2 | **Exactly-once**. Отправка сообщения -> перезапуск консьюмера до коммита -> повторная отправка. | В целевой системе (БД) нет дублей (проверяем идемпотентность на стороне потребителя). |
| 3.3 | **Линейная нагрузка**. Отправка 1 млн сообщений за короткое время. | Продьюсер не вылетает по OutOfMemory, консьюмер не отстает по Lag (проверить `kafka-consumer-groups --describe`). |
| 3.4 | **Смена схемы (Schema Evolution)**. Отправить новую версию JSON с добавленным полем. | Старый консьюмер игнорирует новое поле (не падает), новый консьюмер читает его. |

### 1. Что **НЕЛЬЗЯ** сделать как юнит-тест

Вот эти проверки **нельзя** покрыть обычным `@Test` с моками:

| Проверка | Почему не юнит-тест |
| :--- | :--- |
| Отправка сообщения в реальную Кафку | Нужен **живой брокер**, мок не покажет сериализацию, ретраи, таймауты. |
| Падение REST-модуля и перезапуск | Нужно **поднимать и убивать процесс** — это не уровень юнит-теста. |
| Чтение реальных оффсетов после перезапуска | Нужен реальный `__consumer_offsets` топик. |
| Перебалансировка групп | Только с реальными консьюмерами. |

**Юнит-тесты** здесь бесполезны — они проверяют только логику внутри одного класса, но не поведение Кафки.

---

### 2. Что **МОЖНО** сделать как интеграционный автотест

Самый распространённый подход — **поднимать Кафку в тестах** (через Testcontainers или встроенную Кафку) и писать автотесты, которые проверяют поведение **всего модуля**.

#### Пример: интеграционный тест для продьюсера (gRPC-модуль)

```java
@SpringBootTest
@EmbeddedKafka(partitions = 1, topics = {"test-topic"})
class GrpcProducerIntegrationTest {

    @Autowired
    private GrpcService grpcService; // ваш gRPC-сервис

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    @Test
    void shouldRetryOnBrokerFailure() throws Exception {
        // 1. Останавливаем встроенную Кафку (имитируем падение брокера)
        EmbeddedKafkaBroker broker = ...;
        broker.getKafkaServers().forEach(server -> server.shutdown());
        
        // 2. Пытаемся отправить сообщение через gRPC
        assertThatThrownBy(() -> grpcService.sendMessage("test"))
            .isInstanceOf(TimeoutException.class); // должен упасть по таймауту
        
        // 3. Поднимаем Кафку обратно
        broker.restart();
        
        // 4. Отправляем снова — должно успешно
        grpcService.sendMessage("test");
        
        // 5. Проверяем, что сообщение появилось в топике
        ConsumerRecord<String, String> record = KafkaTestUtils.getSingleRecord(
            consumer, "test-topic"
        );
        assertThat(record.value()).isEqualTo("test");
    }
}
```

### 3. Что **не получится** сделать как автотест (без дополнительных инструментов)

Проверка **№3.2 (дубли при перезапуске REST-модуля)** — это **системный тест**, потому что требует:

1. **Реального убийства процесса** (не просто остановки бина в Spring-контексте).
2. **Перезапуска приложения** с новым PID.
3. **Проверки, что оффсеты сохранились** в реальном топике.

В автотестах (даже интеграционных) вы **не можете** `kill -9` процесс JVM и запустить его заново — тест просто упадёт.

## Как это обычно делают в реальных проектах

### Вариант А (самый частый) — **разделение на уровни**

| Уровень | Что тестируем | Инструменты |
| :--- | :--- | :--- |
| **Юнит-тесты** | Логику обработки сообщения (парсинг, валидацию, маппинг) | JUnit, Mockito (Кафка замокана) |
| **Интеграционные тесты** | Сериализацию, ретраи, таймауты, авто-коммит | `@EmbeddedKafka`, Testcontainers |
| **Системные/E2E тесты** | Перезапуск, падения, оффсеты, дубли | Docker Compose + отдельный тестовый раннер (например, Testcontainers с управлением контейнерами) |

---

### Вариант Б — **автотест с поднятием двух контейнеров** (для проверки падений)

Вы можете написать тест, который **управляет контейнерами** через Testcontainers:

```java
@Test
void testConsumerRestartDoesNotLoseMessages() throws Exception {
    // 1. Поднимаем Кафку, gRPC-модуль, REST-модуль в Docker
    KafkaContainer kafka = new KafkaContainer("latest");
    GenericContainer<?> grpcModule = ...;
    GenericContainer<?> restModule = ...;
    
    // 2. Отправляем сообщение через gRPC
    grpcModule.execInContainer("grpc-client", "send", "test-data");
    
    // 3. Ждём, пока REST-модуль начнёт обрабатывать
    await().until(() -> logsContains(restModule, "Processing message"));
    
    // 4. Убиваем REST-модуль (Docker stop)
    restModule.stop();
    
    // 5. Перезапускаем REST-модуль
    restModule.start();
    
    // 6. Проверяем, что сообщение обработано повторно
    await().until(() -> logsContains(restModule, "Processing message"));
}
```

**Но** такой тест:
- Долго выполняется (подъём контейнеров).
- Сложен в отладке.
- Требует много ресурсов (особенно в CI/CD).

---

### Вариант В — **ручной тест (регрессионный)**

В небольших проектах часто делают **чек-лист**, который тестировщик **прогоняет вручную** перед релизом.

| Шаг | Действие | Ожидаемый результат |
| :--- | :--- | :--- |
| 1 | Отправить сообщение через gRPC | Сообщение появилось в Кафке |
| 2 | REST-модуль начал обработку | Лог «Processing offset 5» |
| 3 | Убить REST-модуль (`kill -9`) | Процесс завершён |
| 4 | Перезапустить REST-модуль | Приложение стартовало |
| 5 | Проверить логи | Сообщение с оффсетом 5 обработано повторно |
| 6 | Проверить REST-ответ | Клиент получил данные |

Это **не автотест**, а **ручной тест-кейс**. Но он обязателен, если у вас нет инфраструктуры для E2E-автотестов.

## Мой совет для вашего проекта

1. **Обязательно сделайте интеграционные автотесты** для пунктов, которые помечены ✅ — это сэкономит вам кучу времени при рефакторинге.
2. Для проверки **№3.2 (перезапуск)**:
    - Если у вас есть DevOps-инфраструктура (Docker, CI/CD) — напишите **один** E2E-автотест с Testcontainers. Это дорого, но надёжно.
    - Если нет — **задокументируйте ручной тест-кейс** и прогоняйте его перед каждым релизом. Это дешевле и проще для маленького проекта.

**Главное**: никогда не пропускайте проверку №3.2 вручную, если у вас нет автотеста — потеря данных в проде обойдётся намного дороже, чем 10 минут ручного тестирования.
