## Подключение как зависимость

**Вывод по результатам битвы.**
1. Есть рабочий пример [springboot-grpc](https://github.com/wiremock/wiremock-grpc-demos/tree/main/springboot-grpc). Особенности примера: 
   * используется новая библиотека springboot-grpc
   * проект примера это один модуль, нет родительского проекта и подпроектов
   * реализация протокола gRPC прямо в этом проекте (ровно один 1-1 запрос типа поздороваться)
   * программно подтягиваются зависимости для wiremock и wiremock-grpc-extension
   * во время настройки спринг контекста в тесте wiremock запускается на случайном порте, этот порт выставляется как системное свойство. А в application.properties указан порт grpc-сервиса через это свойство. Поэтому сервис будет подниматься на этом же порту.
1. Перенос этого примера один в один невозможен в силу структуры проекта. Но натянуть сову я попыталась. Максимальный результат -- сервера запускаются, порт какой надо, grpc мок-сервис запускается, но не может найти метод, который мы вызываем. 
1. Из "смешного" -- дипсик отказался мне помогать с формулировкой "давайте не будем тратить ваше время, новая библиотека сырая, и вообще оно не работает"


## Подключение в режиме standalone
Мой проект устроен так, что один модуль это rest клиент, методы которого внутри себя дергают методы gRPC. Идея в том, чтобы запустить rest-клиент и wiremock-grpc и не запускать реальный grpc сервер. Wiremock должен все запросы перехватывать и правильно отвечать. Правильно это значит так, как это описано в стабах.
Лучше всего поднимать wiremock standalone в докере. В качестве образа берем [вот этот](https://github.com/Adven27/grpc-wiremock).

На что стоит обратить внимание и шаги по старту работы.
1. Папки монтирования 
   * папку /wiremock образа мы монтируем с папкой в проекте, которая содержит папку grpc. В этой папке wiremock будет искать стабы (json с запросвами и ответами).
   * папку /proto монтируем с папкой, в которой лежат наши proto-файлы. Есть нюанс -- если у вас есть валидация, то потредуется положить файл с описанием методов этой валидации рядом с нашими proto-файлами. Образ при старте перегенерирует файлы.
1. Порты и переменные окружения. Традиционно порт админки запускается на порту 8080. Можно там и оставить, если порт свободен.
   * в разделе ports объявляем порты
   * в разделе environment задаем переменные окружения, в которых как раз указываем какой порт куда должен смотреть.
1. Запустить rest-клиент.
1. Запустить докер ( `docker compose -f docker-compose.mock.yml up -d` )
1. Опционально, но крайне полезно смотреть логи: `docker logs wiremock`
1. Остановка докера ( `docker compose -f docker-compose.mock.yml down` )

## Запросы, стабы, админка 

### Структура стаба

Название метода (urlPath) это имя сервиса без пакетов, только имя и имя метода через слеш. 
Подозреваю, что метод всегда POST для стаба. 
Проще всего действительно использовать строку в качестве тела запроса и тела ответа. Но, я думаю, могут быть варианты.
Статус код всегда 200. Хотя для приличия **надо еще проверить**. Возможно, для неуспеха это будет 500, а подробности будут в мета-заголовках.
Можно использовать шаблонизацию (это свойство самого wireomck, оно есть в образе из коробки).
В каком-то руководстве было указано, что заголовок ответа обязательно должен содержать "grpc-status-name".

~~~json
{
  "request" : 
  {
    "urlPath" : "/InventoryCRUD/getInventory",
    "method" : "POST",
    "bodyPatterns" : [
      {
        "equalToJson" : "{ \"id\": \"f070f450-1ee6-4cf1-b7b0-60104e52416d\"}"
      }
    ]
  },
  "response" : 
  {
    "status" : 200,
    "body" : "{\"id\": \"f070f450-1ee6-4cf1-b7b0-60104e52416d\",\"name\": \"Test product\",\"count\": 42}",
    "headers" : 
    {
      "grpc-status-name" : "OK"
    }
  }
}
~~~

### Админка wiremock

Админка запускается на порту 8080 (смотреть как настроено в докере). 

Получить все стабы
~~~text
 curl --location 'http://localhost:8080/__admin/mappings'
~~~
Стаб содержит поля id, uuid с одинаковым значением. Это идентификатор, который присваивается стабу при добавлении его в wiremock. 
Их два для обратной совместимости, как я поняла.

Создать стаб 

~~~text
 curl --location 'http://localhost:8080/__admin/mappings' \
--header 'Content-Type: application/json' \
--data '{
    "request": {
        "method": "POST",
        "url": "/InventoryCRUD/getInventory",
        "bodyPatterns" : [{
          "equalToJson" : "{ \"id\": \"f070f450-1ee6-4cf1-b7b0-60104e52416d\"}"
        }]
    },
    "response": {
        "status": 200, "body" : "{\"id\": \"f070f450-1ee6-4cf1-b7b0-60104e52416d\",\"name\": \"Test product\",\"count\": 42}",
        "headers" : {
          "grpc-status-name" : "OK"
        }
    }
}'
~~~

Удалить стаб
Важно -- в пути указан идентификатор стаба, который надо удалить.
~~~text
curl --location --request DELETE 'http://localhost:8080/__admin/mappings/ca12fb30-8c47-4162-ad5e-89da93e6cc28'
~~~
